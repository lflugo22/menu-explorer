# Plan: Convert Markdown Content to YAML Format

## Problem
The markdown-based content format does not work for arbitrarily deep structures. The current parser relies on markdown heading levels (##, ###, ####, etc.) to determine hierarchy, which has two issues:
1. Markdown only formally supports heading levels 1-6
2. Deep nesting (10+ levels as seen in clx10_sensor.md) becomes unwieldy

## Solution
Convert content files from markdown (.md) to YAML (.yaml) format with explicit nesting via indentation, which naturally handles arbitrary depth.

## Chosen Format: Option A - Modified Markdown

After user preference selection, Option A is chosen. The format keeps the familiar markdown syntax while using list indentation instead of heading depths:

### Concrete Example: clx10_sensor.yaml
```yaml
device_type: clx10_sensor
version: "All"
label: "Chlorine Sensor (CLF10sc / CLT10sc)"
compatible_controllers:
  - sc200
  - sc4500

# Menu content - uses list nesting instead of ## headings
- sensor_setup: "Sensor Setup"
  - configure: "Configure"
    > Enter identification information and display options for the sensor...
    - edit_name: "Edit Name"
      > Changes the name that corresponds to the sensor...
    - select_param: "Select Param."
      > Customizes the options for sensor data handling...
    - reset_defaults: "Reset Defaults"
      > Sets the configuration menu to the default settings...
```

### Format Rules
1. **Metadata** at top level (device_type, version, label, compatible_controllers, etc.)
2. **Nodes** start with `- key: "Label"` pattern
3. **Nesting** via 2-space indentation (any depth allowed)
4. **Descriptions** via blockquote `> text` immediately after the node item
5. **Slot nodes** use `- slot: "Device {{slot_index}}"` for controller templates
6. **Branch nodes** can have both a description and children
7. **Leaf nodes** are list items that have no further indented children

### Handling the Current Markdown Example
Current markdown uses `##`, `###`, `####` etc. - these become:
- `## Sensor Setup` → First level `- sensor_setup: "Sensor Setup"`
- `### Configure` → Second level indented under parent
- `#### Select Parameters` → Third level indented under Configure
- And so on - unlimited depth via indentation

## Parser Logic Details (Option A Format)

The parser needs to:
1. Parse YAML to get structured data
2. Find the content list (starting with `- key: label` items)
3. Use indentation level to determine node depth
4. Handle blockquotes as descriptions for the preceding node

Example token walk:
```
- sensor_setup: "Sensor Setup"          # depth 0, branch
  - configure: "Configure"              # depth 1, branch
    > description text                   # attaches to configure
    - edit_name: "Edit Name"           # depth 2, leaf
      > description                      # attaches to edit_name
```

## Node Record Structure (unchanged)
Each node produces:
```javascript
{
  id: "device_type@version/path",
  version_id: "device_type@version",
  path: "path.to.node",
  key: "node_key",
  label: "Display Label",
  description: "optional description",
  type: "branch" | "leaf" | "slot",
  depth: number,
  parent_id: "parent_path" | null,
  children: ["child_id1", ...],
  sort_order: number,
  controller_labels: { ... }
}
```

## Edge Cases to Handle
- Slot nodes (for controllers) - maintain current `slot:` syntax
- Empty branch nodes → convert to leaf (existing behavior)
- Blockquote descriptions → becomes `description` field on nodes
- controller_labels overrides in frontmatter → keep as metadata field
